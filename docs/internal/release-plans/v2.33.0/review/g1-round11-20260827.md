### R11-F1 - one row carrying two claims defeats a per-row rule

> The new rule treats each policy row as one claim, but the `Who can read a trace` row combines
> authorization and audit logging. A normal authorized-read test plus a degraded stale-grant test
> fills both required columns without proving that reads are logged or readers identifiable. The fix
> removed the prior explicit read-logging check, so the table can appear complete while sensitive
> trace access remains unaudited.

**CONFIRMED, and it is a genuine regression introduced by D22.** The deleted choreography carried an
explicit read-logging assertion. Folding it into a per-row rule was safe only if every row held
exactly one claim, and `Who can read a trace` held two. **A per-row rule is only as good as the row
decomposition underneath it**, which the D22 replacement never checked.

**Closed by splitting the row**: `Who can read a trace` now covers authorization and grant removal,
and a new `Whether a read is logged` row covers audit, with the row text stating why they cannot
share a test. This also aligns the template with `SKILL.md`'s quality checklist, which already named
"access and read-logging" as two concerns.

### R11-F2 - a partial sweep against an explicit list
