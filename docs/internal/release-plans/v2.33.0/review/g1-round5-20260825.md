## The correction this round forces

The round-3 plan entry recorded that **"the release content is close to clean; the instability is
the fix passes"**, on provenance evidence that 7 of 8 round-3 findings sat in files the previous fix
pass had touched. **Round 5 falsifies that conclusion.** Three of these six are pre-existing content
defects that four prior rounds missed, and one of them contradicts the stated basis for three MAJOR
version bumps.

**Why they surfaced only now, stated plainly because it is a method finding.** Rounds 3, 4 and 5 all
led their focus text with "new damage from the fix pass itself". That instruction was correct and
productive each time, but it also **shaped what got looked at**. Only by round 5, with fix-pass
damage thinning, did the review have budget to range over untouched territory. The prompt was part
of the instrument, and it delayed discovery of pre-existing defects by roughly two rounds.

**The counter-frame, which is equally true.** Five genuinely pre-existing defects found across five
rounds, several of them serious, is the gate **working**. It is not evidence that the release is
rotting.

### R5-F1 (vacuous storage-failure test) - high, fix-pass damage

> **Storage failure test can pass without reaching the storage boundary**
> (`skills/measure-instrumentation-spec/references/TEMPLATE.md:173`)
> The normal-path test isolates storage by proving sentinel B reached the collector before checking
> durable storage. The forced-failure test drops that positive assertion and checks only that
> nothing was written. If fault injection or a shared dependency prevents the trace from reaching
> the collector or storage boundary, the test passes vacuously while a broken fail-closed handler
> remains untested.

**CONFIRMED, and it is the same error class as R4-F1 one layer down.** The round-4 fix added the
present-at-collector assertion to the normal path and not to the forced-failure path. Fixed: the
forced storage-failure case now keeps egress healthy and asserts both that B reached the collector
and that the fault actually fired, before checking durable sinks.

### R5-F2 (required sections labeled optional) - high, PRE-EXISTING

> **Required conditional sections are still labeled optional in shipped templates**
> (`skills/deliver-prd/references/TEMPLATE.md:113-114`)
> The SKILL and HISTORY contracts say AI Behavior and Evaluation is required when model output
> triggers it, yet the template labels it OPTIONAL. Agent Execution Contract repeats the defect at
> line 180, and develop-adr does the same for Model Choice at line 62.

**CONFIRMED, and this is the most consequential finding of the cycle after R3-F2.** D11 retyped
three skills to MAJOR on the reasoning that a conditional section is **required for the population
its condition selects**. Three templates said `OPTIONAL`. `measure-instrumentation-spec` already
said `CONDITIONAL`, which is what made the inconsistency visible. The shipped artifact contradicted
the stated rationale for its own version classification, and four rounds walked past it. All three
now read `CONDITIONAL` and state the requirement explicitly.

### R5-F3 (fabricated research provenance) - high, PRE-EXISTING

> **Regenerated persona example fabricates validated research evidence**
> (`skills/foundation-persona/references/EXAMPLE.md:211-216`)
> The example asserts five interviews, 312 support tickets, four customer tenants, and three
> recorded sessions, then labels conclusions validated. The only in-repo source for this Rhea
> persona is the Workbench sample prompt, which supplies none of those studies. This teaches an
> evidence-calibrated persona skill to invent precise provenance and promote it to validated
> evidence.

**CONFIRMED, and it exposes a validator scope gap that is the em-dash gap's twin.** The file
contained **zero** `[fictional]` markers while every comparable sample in `library/` uses them
throughout. `check-sample-no-fabricated-metrics.mjs` globs
`library/skill-output-samples/**/sample_*.md` only, so `skills/*/references/EXAMPLE.md` is invisible
to it, and it runs `continue-on-error: true` in CI besides. The validator built for exactly this
defect cannot see the file the defect is in. Fixed by marking throughout and redefining the
"validated" label as traceable-to-a-source rather than plausible. **Scope gap carried to v2.34.0.**

### R5-F6 (incomplete fallback coverage) - medium, PRE-EXISTING

> **Partial-install fallback omits several skills this review routes to**
> (`skills/foundation-build-risk-review/SKILL.md:82-88`)

## Self-check on the round-5 fix pass, before round 6

The round-5 fixes were unavoidably claim-adding (marking, relabelling, new fallback rows), so the
pass was audited against its own rules before being handed to round 6. Two defects found and fixed
without waiting to be told:

1. **The persona marking was partial.** The inserted comment said "every source, count and quote
   *below*", covering the ledger, while two claims sat **above** it: a frontmatter line reading
   "built from 5 interviews" and a `**Key quote:**` presented as real interview material. This is
   R4-F4's lesson repeating: marking one location of a fact is not marking the fact.
2. **Version-stamped rationale was embedded in template comments.** Three comments ended "That is
   why 3.0.0 is a major rather than a minor." A template outlives the version that produced it, and
   at 4.0.0 the sentence is false. This is X-03's rot class exactly. The requirement claim carries
   the load without naming a version, so the version sentence was removed from all three.
